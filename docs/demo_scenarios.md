# 시나리오 A~D 데모 가이드 (Phase 7)

LLM 대화로 hwpx 문서를 채우고(A) 수정하고(B) 부분 선택 편집하고(C) 일반 질의(D)하는
end-to-end 데모의 재현 절차다. 시나리오 정의 원본은 `DESIGN.md` §3에 있다.

각 시나리오는 **자동 테스트**(FakeBackend로 네트워크 없이 백엔드 구간 검증)와
**육안 확인**(브라우저 조작 UX·한컴오피스/워드 렌더링 등 자동화 불가 구간)으로 나뉜다.

| 시나리오 | 자동 테스트 | 육안 확인 구간 |
|---|---|---|
| A. 표준 양식 채움 | `tests/test_e2e_scenarios.py` | §6.1 한컴오피스 확인 |
| B. 기존 문서 대화 수정 | `tests/test_e2e_scenarios.py` | §6.1 한컴오피스 확인 |
| C. 부분 선택 편집 | `tests/test_e2e_scenarios_cd.py` | §4 클릭 선택 UX + §6.1 표 서식 |
| D. 일반 질의(RAG) | `tests/test_e2e_scenarios_cd.py` | §7 실 RAG 답변 품질 |

```
.venv\Scripts\python -m pytest tests\test_e2e_scenarios.py tests\test_e2e_scenarios_cd.py
```

## 1. 사전 준비

### 1.1 환경 설정 (.env)

저장소 루트에서 `.env.example`을 `.env`로 복사한다.

```
copy .env.example .env
```

- `UNI_RAG_BASE_URL`, `UNI_RAG_MODEL_KEY`는 기본값 그대로 사용한다.
- 로그인 계정은 **UNE 계정**을 사용한다. 앱은 로그인 화면에서 계정/비밀번호를
  입력받아 UNI RAG에 위임 인증하므로 `.env`에 계정을 넣을 필요는 없다.
  (`TEST_UNE_ACCOUNT`/`TEST_UNE_PASSWORD`는 `-m integration` 통합 테스트 전용 선택 항목.
  **계정 값은 문서·커밋에 남기지 않는다.**)

### 1.2 빌드·실행 (Windows, 저장소 루트 기준)

```
:: 백엔드 의존성
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt

:: 프론트 빌드 (산출물 web/dist를 백엔드가 서빙)
cd web && npm install && npm run build && cd ..

:: 백엔드 실행
.venv\Scripts\python -m uvicorn app.main:app --port 8080
```

브라우저에서 `http://127.0.0.1:8080` 접속 → 로그인 화면에 UNE 계정 입력.
(개발 중에는 `cd web && npm run dev`로 5173 포트 개발 서버를 써도 된다. `/api`는 8080으로 프록시.)

### 1.3 데모용 양식 hwpx 준비

placeholder(`[기관명]`, `<담당자 이름>`, `YYYY년 MM월 DD일`, `TBD` 등)가 포함된
표준 양식 hwpx를 준비한다. 실양식이 없으면 테스트 픽스처와 동일한 임시 양식을
생성해 쓸 수 있다.

```
.venv\Scripts\python -c "from app.core.hwpx import build_hwpx; build_hwpx({'title': '재난 대응 계획서 (데모)', 'paragraphs': ['본 문서는 데모용 임시 양식이다.'], 'tables': [{'rows': [['구분','내용'],['수립 주기','연 1회']]}], 'placeholders_demo': True}, 'demo_form.hwpx')"
```

> **실양식(실제 재난 계획서 hwpx)으로 데모하는 경우**: 데모 전에
> `docs/hwpx_validation.md` §4.3의 **실양식 재실측 체크리스트**(extract → validate →
> parse → data-id 불변식 → placeholder 탐지 → 편집 왕복 → 한컴 열람)를 먼저 수행해
> 파서가 해당 양식 구조를 지원하는지 확인한다.

## 2. 시나리오 A — 표준 양식 채움 (주 시나리오)

| 단계 | 조작·입력 발화 | 기대 화면·결과 |
|---|---|---|
| A-1 | 좌측 상단에서 `demo_form.hwpx` 업로드 | 우측 미리보기에 양식이 표시되고 `[기관명]`, `<담당자 이름>`, `TBD` 등 placeholder가 보인다 |
| A-2 | 채팅 입력: **"이 양식으로 재난대응 계획서 초안 작성해줘. 시설 개요는 시민종합회관이야."** | 상태 표시(의도: fill) → 답변 말풍선("양식 채움을 완료했습니다. N개 항목…") → 미리보기가 **버전 1**로 갱신되고 채워진 노드가 하이라이트된다. placeholder가 실제 내용으로 대체됨 |
| A-3 | 추가 지시: **"담당자를 홍길동으로 바꿔줘"** | 상태 표시(의도: edit) → 담당자 문단만 교체되어 **버전 2**로 갱신·하이라이트. 다른 내용은 그대로 |
| A-4 | 미리보기 상단 **다운로드(hwpx)** 클릭 | `재난 대응 계획서 (데모).hwpx` 다운로드 |
| A-5 | 다운로드 파일을 **한컴오피스(한글)** 로 열기 | §6 육안 확인 항목 점검 |

**자동 검증** (`tests/test_e2e_scenarios.py::test_scenario_a_fill_form_then_edit_then_export`와 동일):

- `document_updated` 이벤트의 `changed_ids`가 비어 있지 않고, 버전이 1 → 2로 증가한다.
- export한 hwpx가 `validate_hwpx` 검증(zip 구조·mimetype·섹션 XML)을 통과한다.
- 재파싱 시 `담당자: 홍길동` 등 편집 텍스트가 존재하고, placeholder 패턴
  (`[...]`, `<...>`, `YYYY/MM/DD`, `○○`, `TBD`)이 하나도 남지 않는다.

**육안 확인**: A-5의 한컴오피스 렌더링(§6.1) — 자동 테스트가 대신할 수 없다.

## 3. 시나리오 B — 기존 문서 대화 수정

| 단계 | 조작·입력 발화 | 기대 화면·결과 |
|---|---|---|
| B-1 | 기존 hwpx 문서 업로드 (데모는 A와 같은 파일 사용 가능) | 미리보기에 원문 표시 |
| B-2 | 채팅 입력: **"개요 문단을 'hwpx 문서 생성 고도화'로 수정해줘"** | 상태 표시(의도: edit) → 해당 문단(`data-id` 앵커)만 교체되어 버전 1로 갱신, 바뀐 문단이 하이라이트 |
| B-3 | 다운로드(hwpx) → 한컴오피스로 열기 | 수정 문단 외 문단·표·서식이 원본 그대로 (§6.1) |

**자동 검증** (`tests/test_e2e_scenarios.py::test_scenario_b_edit_existing_document_preserves_rest`와 동일):

- `changed_ids`가 정확히 대상 노드 1개다.
- export 재파싱 시 대상 노드 텍스트만 `hwpx 문서 생성 고도화`로 바뀌고,
  나머지 모든 노드는 원문과 동일하다 (부분 수정·원본 서식 보존).

## 4. 시나리오 C — 부분 선택 편집

미리보기에서 문단·표 셀을 **클릭으로 선택**한 뒤 지시하면, 선택한 `data-id` 노드만
편집 대상이 된다 (M4-4·M6-5). 현재 구현은 클릭 토글 방식이다
(`DESIGN.md` §3의 "드래그 선택"은 클릭 다중 선택으로 구현 — 같은 목적의 UX).

| 단계 | 조작·입력 발화 | 기대 화면·결과 |
|---|---|---|
| C-1 | hwpx 업로드 (A와 같은 `demo_form.hwpx` 사용 가능) | 미리보기에 문단·표가 표시된다 |
| C-2 | **[육안]** 미리보기에서 표의 셀(또는 문단) 하나를 클릭 | 클릭한 요소에 선택 표시(테두리/배경)가 생기고, 미리보기 툴바에 **"선택된 요소 1개"** 와 [해제] 버튼이 나타난다 |
| C-3 | **[육안]** 다른 셀을 하나 더 클릭 / 이미 선택한 요소를 다시 클릭 | 선택 개수가 2개로 증가 / 재클릭한 요소는 선택 해제(토글) |
| C-4 | 채팅 입력: **"이 부분을 더 격식 있는 문장으로 수정해줘"** | 상태 표시(의도: edit) → 답변 말풍선 → **선택한 노드만** 교체되어 버전 +1, 바뀐 노드가 하이라이트된다 |
| C-5 | 적용 직후 화면 확인 | 선택이 **자동 해제**되어 "선택된 요소" 표시가 사라진다. 선택하지 않았던 문단·셀은 원문 그대로 |
| C-6 | (선택) 편집 없이 선택만 지우려면 툴바 [해제] 클릭 | 선택 표시가 모두 사라진다 |
| C-7 | 다운로드(hwpx) → 한컴오피스로 열기 | 편집한 셀의 표 서식(병합·테두리) 보존 확인 — §6.1 항목 6 |

**자동 검증** (`tests/test_e2e_scenarios_cd.py` — 백엔드 selection 파이프라인):

- `/chat`에 `selection: [data_id...]`을 실어 보내면 편집 후보가 선택 노드로 필터된다.
- `changed_ids`가 선택한 id의 부분집합이다 — LLM이 선택 밖 id를 반환해도 폐기된다.
- 선택하지 않은 노드는 export 재파싱 시 원문과 동일하다.
- 존재하지 않는 id만 선택해 보내면 "편집할 대상 노드가 없습니다…" 안내가 오고
  문서·버전은 불변이다.

**육안 확인** (브라우저 클릭 UX — pytest로 자동화 불가, 반드시 사람이 점검):

- [ ] 클릭 시 선택 표시가 즉시 나타나고, 재클릭 시 토글 해제되는가 (C-2·C-3)
- [ ] 툴바의 선택 개수 표시와 [해제] 버튼이 동작하는가 (C-2·C-6)
- [ ] 편집 적용 후 선택이 자동 해제되는가 (C-5)
- [ ] 하이라이트가 선택했던 요소에만 나타나는가 (C-4)

> 발화 팁: 실 LLM 사용 시 의도 분류 폴백(§7)에 걸리도록 "수정해줘"처럼 edit 키워드를
> 포함하는 것이 안전하다. "이 부분을 더 격식 있는 문장으로"만 보내면 분류가 query로
> 흔들릴 수 있다.

## 5. 시나리오 D — 일반 질의 (RAG)

문서 편집이 아닌 지식 질문은 UNI RAG의 검색 응답을 **채팅에만** 표시하고 문서는
건드리지 않는다. 답변 내용을 후속 지시로 문서에 반영할 수 있다.

| 단계 | 조작·입력 발화 | 기대 화면·결과 |
|---|---|---|
| D-1 | 문서가 열린 상태에서 채팅 입력: **"풍수해 대응 매뉴얼에서 대피 기준이 뭐야?"** | 상태 표시(의도: query, "답변 생성 중") → 답변 말풍선만 추가된다 |
| D-2 | 우측 미리보기·툴바 확인 | 미리보기 내용·하이라이트 변화 없음, **버전 번호(vN)가 그대로** — 문서 불변 |
| D-3 | 후속 지시: **"그 내용으로 개요 문단 채워줘"** | 의도 fill(또는 edit)로 전환 → 대화 히스토리의 직전 답변을 근거로 문서에 반영, 버전 +1·하이라이트 |
| D-4 | (참고) 문서 업로드 전에 질문해도 | 문서가 없으면 항상 query로 처리되어 일반 대화가 가능하다 |

**자동 검증** (`tests/test_e2e_scenarios_cd.py` — 문서 불변식):

- query 턴은 `edits`가 빈 배열이고 `document_updated` 이벤트가 발생하지 않는다.
- query 턴 전후로 문서 버전·HTML이 동일하다.
- 후속 fill/edit 턴에서 대화 히스토리(직전 질의·답변)가 LLM에 전달되어
  "그 내용으로"류 지시가 성립하고, 문서가 갱신된다.

**육안 확인 / 실 RAG 주의사항**:

- [ ] D-2에서 버전 번호가 실제로 변하지 않는가 (채팅만 갱신)
- [ ] D-3에서 답변 내용이 문서에 반영되는가
- **RAG 답변 품질은 학습 문서에 좌우된다**: UNI RAG에 재난 도메인 문서(매뉴얼 등)가
  학습되어 있지 않으면 D-1의 답변이 일반 지식 기반이거나 부정확·환각일 수 있다.
  데모 전 RAG 서버 관리자와 협의해 도메인 문서 업로드(`/documents/upload`) 여부를
  확인한다 (`DESIGN.md` §8 항목 5). 미학습 상태로 데모할 때는 "답변 내용의 정확성"이
  아니라 "질의는 문서를 바꾸지 않고, 후속 지시로 반영된다"는 **동작 흐름**을 시연
  포인트로 삼는다.

## 6. 육안 확인 절차 — 한컴오피스(hwpx) / MS Word(docx)

> 상세 배경과 자동 검증(`validate_hwpx`)의 한계는 `docs/hwpx_validation.md` §1~§3 참조.
> 실양식으로 검증할 때는 같은 문서의 **§4.3 실양식 재실측 체크리스트**를 함께 수행한다.

### 6.1 hwpx — 한컴오피스(한글) 확인

다운로드한 hwpx를 한컴오피스(한글) 또는 무료 한글뷰어로 열어 다음을 확인한다.

1. 파일이 오류·복구 안내 없이 정상으로 열린다.
2. 문단 수·순서가 원본과 같고, 편집한 문단만 새 텍스트다.
3. 표의 행·열 구조와 셀 텍스트가 유지된다 (편집한 셀 제외).
4. 글꼴·크기·정렬 등 서식이 원본과 동일하다 (텍스트만 교체하므로 서식은 변하지 않아야 정상).
5. placeholder 표식(`[ ]`, `< >`, `YYYY`, `○○`, `TBD`)이 남아 있지 않다 (시나리오 A).
6. **선택 편집한 표 셀(시나리오 C)**: 편집한 셀의 **셀 병합·테두리·배경 등 표 서식이
   원본 그대로**이고, 셀 안의 텍스트만 바뀌어 있다. 같은 표의 다른 셀은 텍스트·서식
   모두 원본과 동일하다.

### 6.2 docx — MS Word(또는 한컴오피스) 확인

docx는 M2-1 범위의 **내용 전달용 사본**이다 (문단 텍스트 + 표 격자만 재구성.
글자 서식·이미지·셀 병합·페이지 설정은 범위 외 — `app/core/docx/exporter.py` 참조).

**다운로드 방법**: 화면의 다운로드 버튼은 hwpx 전용이므로, docx는 export API를 직접
호출한다 (문서 id는 브라우저 개발자도구 Network 탭의 `/api/documents/...` 요청이나
`GET /api/documents` 목록에서 확인).

```
:: 1) 도구 세션 토큰 발급 — 계정 값은 셸에서 직접 입력하고 파일·문서에 남기지 않는다
curl -s -X POST http://127.0.0.1:8080/api/auth/login -H "Content-Type: application/json" -d "{\"account\":\"<UNE 계정>\",\"password\":\"<비밀번호>\"}"

:: 2) 응답의 token으로 docx export
curl -s -X POST http://127.0.0.1:8080/api/documents/<document_id>/export -H "Authorization: Bearer <토큰>" -H "Content-Type: application/json" -d "{\"format\":\"docx\"}" -o demo.docx
```

MS Word(또는 한컴오피스)로 `demo.docx`를 열어 확인한다.

- [ ] 오류·복구 안내 없이 정상으로 열린다.
- [ ] 모든 문단 텍스트가 존재하고 한글이 깨지지 않는다 (`占쏙옙`·`?` 없음).
- [ ] 편집·채움한 텍스트(예: `담당자: 홍길동`)가 반영되어 있다.
- [ ] 표가 원본과 같은 행·열 격자로 나오고 셀 텍스트가 맞다.
- [ ] (정상 한계 — 결함 아님) 글자 서식·이미지·셀 병합은 재현되지 않으며,
      원문에서 문단 중간에 있던 표가 docx에서는 해당 문단 **앞**에 나올 수 있다.
- [ ] 다른 이름으로 저장이 정상 동작한다.

## 7. 실 LLM(UNI RAG) 사용 시 주의

자동 테스트는 FakeBackend로 결정적 응답을 쓰지만, 실 서버 데모는 LLM 품질 편차가 있다.

- **의도 분류 편차**: 같은 발화도 edit/fill/query 분류가 흔들릴 수 있다. 분류 JSON이
  깨지면 키워드 휴리스틱("작성/채워/초안" → fill, "수정/바꿔/변경/고쳐" → edit)으로
  폴백하므로, 데모 발화에는 해당 키워드를 명시적으로 넣는 것이 안전하다
  (시나리오 C의 발화 팁 참조).
- **JSON 재시도**: 편집/채움 응답이 JSON으로 복구되지 않으면 동일 프롬프트로 1회
  재요청한다. 재요청도 실패하면 채팅에 `llm_unavailable` 오류가 표시된다 — 같은 지시를
  다시 보내면 대부분 성공한다.
- **채움 품질**: placeholder가 많은 양식은 30노드 단위 청크로 나눠 여러 번 호출하므로
  응답에 수십 초가 걸릴 수 있다 (타임아웃 기본 120초). 일부 항목이 채워지지 않으면
  답변의 `[참고]` 문구(적용 불가 사유)를 확인하고 해당 항목만 추가 지시로 채운다.
- **RAG 질의 품질(시나리오 D)**: 재난 도메인 문서가 RAG에 학습되어 있지 않으면 답변
  품질이 제한된다 — §5의 주의사항대로 데모 전 학습 여부를 확인하고, 미학습 시에는
  동작 흐름 시연에 집중한다.
- **환각 주의**: 채움 내용(기관명·날짜·연락처 등)은 LLM 생성물이므로 반드시 사람이
  검토·수정한 뒤 사용한다. 발화에 실제 값을 구체적으로 제공할수록 정확하다.
