# 알려진 제약사항·향후 과제

- 작성일: 2026-07-11 (Phase 7)
- 근거: 코드 실측 (`app/core/hwpx/html.py`, `app/core/docx/exporter.py`, `app/services/orchestrator.py`, `app/llm/`) 및 Phase 4~6 검증 기록

## 1. 알려진 제약사항

### 1.1 실양식(재난 계획서 hwpx) 미확보

- 표준 재난 계획서 hwpx 양식을 아직 입수하지 못해, **python-hwpx 동봉 템플릿 등 임시 양식으로 대체 검증**했다.
- 실양식 입수 시 재실측 체크리스트가 [`hwpx_validation.md`](hwpx_validation.md) §4(4.3)에 있다. 실양식에 수식·도형 등 미지원 요소(§1.3)가 포함되면 렌더 범위 재평가가 필요하다.

### 1.2 한컴오피스 육안 렌더링 확인 필요

- 자동 검증(`validate_hwpx` + pytest 스위트)은 **구조 수준**(zip·mimetype·필수 엔트리·XML 파스, 텍스트·주소 무결성)까지만 보장한다.
- 실제 한컴오피스/한글뷰어에서의 렌더링(서식·표 병합·이미지·줄바꿈)은 **육안 확인이 별도로 필요**하다. 확인 절차와 항목은 [`hwpx_validation.md`](hwpx_validation.md) §3 참조.

### 1.3 hwpx → HTML 렌더링 미지원 요소

- `app/core/hwpx/html.py`는 문단(hp:p)·표(hp:tbl)·이미지(hp:pic)만 렌더하며, **수식·도형·각주 등(secPr·ctrl 포함)은 렌더를 생략**한다.
- 생략된 요소는 미리보기에 보이지 않지만, 편집 대상이 아니므로 원본 XML에는 그대로 남는다("원본 보존·미편집" 원칙). 즉 미리보기 누락 ≠ 데이터 손실.

### 1.4 docx 변환 범위 (M2-1)

`app/core/docx/exporter.py`의 실제 구현 범위:

- **보존되는 것**: 문단 텍스트, 표 격자(행·열 주소, `Table Grid` 스타일).
- **제외되는 것**: 글자 서식(폰트·크기·색), 이미지, 셀 병합, 페이지 설정.
- 순서 제약: 원문에서 표가 문단 중간에 끼어 있어도 docx에서는 "표 → 문단" 순서로 출력된다 (파서의 노드 순번 규칙상 표 셀이 담는 문단보다 먼저 나오기 때문).
- 요컨대 docx 출력물은 **"내용 전달용" 사본**이며, 서식 보존 출력은 hwpx 다운로드를 사용해야 한다.

### 1.5 LLM 품질 편차

- **의도 분류 흔들림**: LLM 분류가 애매한 발화에서 edit/fill/query를 오판할 수 있다. 키워드 기반 **휴리스틱 폴백**이 있어 LLM 분류 실패 시에도 동작은 하지만, 폴백 정확도는 제한적이다.
- **JSON 응답 깨짐·잘림**: 구조화 응답은 **JSONL 스트리밍**(`app/llm/jsonl_stream.py` — 한 줄에 edit 하나, 완성 줄 단위 반영)으로 받고, 계약 위반 응답은 4단계 복구 파서(`app/llm/json_parser.py`)로, max_tokens로 잘린 응답은 **부분 복구**(`parse_llm_json_or_partial` — 완성 항목만 채택)로 대응한다. 복구분이 있으면 반영 후 "일부만 반영" 안내가 붙고, 전혀 못 살릴 때만 1회 재요청 후 에러로 안내된다. fill은 청크 단위로 격리되어 **한 청크가 실패해도 나머지 청크 결과는 적용**된다(실패 구간은 참고 사항으로 안내).
- qwen3-coder-next의 한국어 공문서 품질은 1차 실측에서 양호했으나(공문서 어투 교정·순수 JSON 준수), 체계적인 품질 벤치마크는 미수행이다.

### 1.6 T3Q 플랫폼 의존성 (2026-07-14 전환)

- 목차·본문 생성과 편집 모드 LLM 대화가 모두 T3Q 플랫폼(`https://plf.mois-disaster.t3q.ai`) 단일 서버에 의존한다. **서버 다운 시 생성·채팅 기능 불가** (hwpx 업로드·미리보기·다운로드는 동작).
- **TLS 인증서 불일치**: 배포받은 `certs/cadm-ca.crt`는 UNE 자체 서명 CA로, T3Q 서버 인증서(발급자 `*.t3q.ai`)를 검증하지 못한다 — 올바른 CA 확보 전까지 `T3Q_TLS_VERIFY=false` 우회 운용 (`docs/t3q_upgrade_design.md` §6).
- T3Q API는 현재 무인증(실측)이다. 인증 도입 시 `t3q_client.py`에 헤더 주입이 일원화되어 있다.
- 로그인 기능은 삭제되었다 — 익명 단일 로컬 사용자 전제 (다중 사용자·SSO는 향후 과제).

### 1.7 단일 인스턴스 전제

- SQLite + 로컬 파일저장소(`data/files/`) + 프로세스 내 SSE 스트림 구조이므로 **단일 서버 프로세스 전제**다. 다중 인스턴스(로드밸런싱)로 띄우면 DB 잠금·파일 불일치·SSE 세션 단절이 발생한다.
- Postgres 이관 대비 설계(표준 SQL 서브셋, `app/db/` 캡슐화)는 되어 있으나 실제 이관·검증은 범위 외.

### 1.8 미리보기 페이지 수 ≠ 실제 페이지 수

- HTML 미리보기의 `.page` 분할은 **섹션 단위**(`html.py`, min-height)라서, 내용이 늘어나면 페이지 div가 세로로 길어질 뿐 페이지 수는 늘지 않는다. 즉 미리보기의 페이지 수는 한컴오피스에서 열었을 때의 실제 페이지 수와 다를 수 있다.
- **hwpx 출력물은 정상**: `apply_edits`가 편집 문단의 줄배치 캐시(linesegarray)를 제거하므로, 한컴오피스가 열 때 줄 수·페이지를 재계산해 내용 증가분만큼 페이지가 자연히 늘어난다. 페이지 수 판단은 한컴 기준으로 하라.

### 1.9 응답 분량 제약 (max_tokens)

- 생성 길이 상한(`LLM_MAX_TOKENS`, 기본 4096)을 요청에 동봉하지만 **서버(UNI RAG)가 이를 실제 반영하는지는 보장되지 않는다**(passthrough 미협의). 응답이 서버 상한에서 잘릴 수 있다.
- 잘린 응답은 §1.5의 JSONL 스트리밍·부분 복구로 **완성된 항목까지 반영**되고 "일부만 반영" 안내가 붙는다. 장문 생성이 필요하면 미리보기에서 범위를 좁혀(선택 후) 나눠 요청하는 것을 권장한다.

### 1.10 새 문단·노드 추가 불가

- `apply_edits`는 **기존 노드의 텍스트 교체 전용**이다 — 문단·표 행·셀의 추가/삭제/이동은 지원하지 않는다(빈 문자열 치환으로 "내용 지우기"만 가능).
- 따라서 생성할 내용이 템플릿의 노드 수보다 많아도 문서 구조가 늘어나지 않는다. 긴 내용은 한 노드 안에 이어 쓰이며(개행은 공백으로 합쳐짐), 구조 확장은 향후 과제(문단 복제 방식)다.

## 3. 보안 주의사항

- **`.env` 커밋 금지** — gitignore 등재. `개발 배경 및 목적.txt`는 로컬 전용 파일이다 (실계정 미포함 — 2026-07-13 확인).
- **TLS 검증 우회는 임시** — `T3Q_TLS_VERIFY=false`는 인증서 체인 불일치(§1.6)에 대한 임시 조치다. 올바른 CA 확보 즉시 검증을 켜야 한다.
- 미리보기·생성 본문 HTML은 프론트에서 DOMPurify로 sanitize 후 렌더되지만, 신뢰할 수 없는 출처의 hwpx 업로드는 지양한다.
