# 레퍼런스 hwpx 양식(서식1 사업계획서) 인지·채움 실패 — 원인 분석 및 개선안 (보완판)

작성일: 2026-07-12 (v2) · 대상: une_report 코드 + 서식1 사업계획서신청용.hwpx 실측
v2 보완: §1 오픈소스 사용 실태, §2.0 인식 실패의 층위 구분, 원인 6(신규 생성 경로 미연결), §4 UNI 서버 협의 불가 시 대응

## 0. 결론 요약

코드 결함이 아니라 **설계 전제와 실양식의 불일치**가 원인이다. 시스템은 "regex 토큰([기관명], ○○ 등)이 박힌, 텍스트가 이미 들어있는 노드"를 채우도록 설계됐는데, 실양식은 **파란 기울임체 가이드 문구 + 빈 표 셀**로 채울 곳을 표시한다. 그 결과 (1) 채울 곳의 97%를 인지하지 못하고, (2) 인지했더라도 노드의 68%는 hp:t가 없어 물리적으로 쓸 수 없다. 또한 LLM 응답으로 새 문서를 만드는 모듈(build_hwpx)은 존재하지만 채팅 파이프라인에 연결되지 않았다. 개선의 핵심 작업은 전부 클라이언트 측이며, UNI 서버 협의 없이 진행 가능하다(§4).

## 1. 오픈소스 사용 실태 (질의 대응)

"Process-GPT만 쓴 것인가, rhwp·hwpConverter도 쓴 것인가"에 대한 코드 실측 결과:

| 오픈소스 | 실제 반영 | 근거 |
|---|---|---|
| process-gpt-office-mcp | **패턴 채택** — HWPX↔HTML 왕복 편집(data-id 앵커) 구조를 자체 구현 | html.py 주석에 참조 명시 |
| process-gpt-completion | **부분 참고** — LLM JSON 복구 파서 방식 응용 | json_parser.py 주석에 참조 명시 |
| python-hwpx (라이브러리) | **보조 채택** — 신규 문서 생성(builder.py), 테스트 픽스처 | requirements 의존성 |
| rhwp | **미사용** — 조사 문서에서 "참고(직렬화 함정 사례집)"로 분류, 코드 반영 0줄 | docs/analysis.md §3.1 |
| hwpConverter | **미사용** — "참고(제외에 가까움)"로 분류, 코드 반영 0줄 | docs/analysis.md §3.2 |

즉 hwpx 파싱·편집 코어는 표준 라이브러리(zipfile+ElementTree)로 자체 작성됐고, rhwp·hwpConverter는 Phase 1 조사 보고서에만 존재한다. 이 선택 자체는 타당했다(rhwp는 Rust/WASM 렌더러 중심, hwpConverter는 일괄 변환기라 문단 단위 편집에 부적합). 문제는 오픈소스 선택이 아니라 아래 §2의 설계 공백이다.

## 2. 원인 분석

### 2.0 "인식 실패"의 층위 — 어디까지 되고 어디부터 안 되는가

업로드 hwpx의 **물리적 파싱은 성공한다**: 서식1에서 5,386개 노드, 전체 텍스트의 95%를 정상 추출했다. 실패는 그 위 세 층위에서 발생한다.

1. **의미 인식**: 읽은 노드 중 어디가 "채울 곳"인지 판별 못 함 (원인 1)
2. **구조 전달**: 표의 라벨-값 관계를 추출하고도 LLM에 안 넘김 (원인 3)
3. **쓰기**: 판별했더라도 빈 셀 68%는 물리적으로 쓸 수 없음 (원인 2)

"업로드 파일 인식을 제대로 해야 한다"는 요구는 곧 1·2번 층위(의미 해석 계층)를 신설하고 3번을 뚫는 작업이다.

### 실측 수치 (서식1을 실제 파이프라인에 통과시킨 결과)

| 항목 | 값 |
|---|---|
| 전체 노드 | 5,386개 (본문 506 + 표 셀 4,880 / 표 89개, section 2개) |
| placeholder 정규식 탐지 | **36건** (bracket 3, angle 9, filler 24) — `[서식1]`, `<설계도>` 등 비채움 대상 오탐 포함 |
| 파란 기울임체 "작성 가이드" run | **221개, 약 5,900자** (charPr 61종) — 실제 채움 지시인데 전혀 탐지 안 됨 |
| 텍스트 빈 노드 | 3,777개 (70%) |
| **hp:t 자체가 없는 노드** | **3,687개 (68%)** — apply_edits가 무조건 skip |
| 편집 프롬프트에 전체 노드 나열 시 | 약 116,000자 (≈4~6만 토큰) |
| 파서 텍스트 커버리지 | 18,258 / 19,203자 (캡션·머리말 등 약 5% 누락) |

### 원인 1 — 채움 대상 "인지" 방식의 불일치 (가장 크다)

`placeholder.py`는 `[x]`, `<x>`, `YYYY`, `○○/XX/TBD` 정규식만으로 채움 대상을 찾는다. 그러나 이 양식(정부 R&D 표준 서식류 공통)은 채울 곳을 두 가지로 표시한다.

- **파란 기울임체 가이드 문구**: "상용화 대상 제품·서비스 명칭 작성", "…500자 내외" 등 221개 run. 양식 첫 줄부터 "※ 파랑색 기울임체로 기재된 작성 가이드는 삭제하고 제출"이라고 명시하지만, 파서는 스타일(charPrIDRef→header.xml)을 아예 읽지 않는다(style_mapper가 Phase 4에서 범위 제외됨).
- **빈 표 셀**: 라벨 셀 옆의 값 셀. 텍스트가 없으므로 어떤 정규식에도 안 걸린다.

결과: `_run_fill`의 대상 축소 로직(`targets = placeholder 있는 노드`)이 5,386개 중 36개만 남기고, 나머지 채움 대상 전부가 LLM에게 보이지도 않는다. "채울 수 있는 항목을 찾지 못했습니다"가 정상 동작이 되는 구조다.

### 원인 2 — 빈 셀은 물리적으로 채울 수 없음

`edits.py`의 교체 규칙은 "첫 hp:t에 new_text를 넣는" 방식이라 **hp:t가 없는 노드는 무조건 skip**된다. 실양식은 한컴에서 직접 만든 문서라 빈 셀에 hp:t가 없고, 그런 노드가 3,687개(68%)다. 즉 LLM이 올바른 id로 edits를 반환해도 적용 단계에서 전부 버려진다. (프로젝트 "개선 검토 사항" 1번 지적이 실측으로 확인된 것. 검증에 쓴 python-hwpx 생성 템플릿은 빈 셀에도 hp:t가 생성되기 때문에 테스트에서 이 병목이 드러나지 않았다 — limitations.md 1.1 "실양식 미확보"의 직접적 결과.)

### 원인 3 — 표 구조 정보가 LLM에 전달되지 않음

파서는 table_idx/row/col/span을 추출하지만 `document_store.get_nodes()`가 `{id, text, type(para/cell)}`만 남기고 버린다. 프롬프트는 "id [cell] 텍스트" 평문 나열이라, LLM 입장에서는 표 경계도, "이 빈 셀이 어느 라벨의 값 칸인지"도 알 수 없다. 양식을 "다 인지하지 못한다"고 체감되는 핵심 이유다.

### 원인 4 — 규모 초과 및 응답 잘림

edit 의도면 노드 5,386줄(≈11.6만 자)을 프롬프트 하나에 싣는다. UNI RAG가 RAG 청크·서버 프롬프트까지 얹는 구조라 컨텍스트 초과·응답 잘림(JSON 파싱 실패)으로 이어진다. 클라이언트가 max_tokens를 보내지 않아 서버 기본 상한(통상 512~1024토큰, 한국어 기준 반 페이지)이 그대로 적용된다. fill에서 placeholder가 하나도 없으면 대상이 전체 노드가 되어 30개씩 **180회 순차 LLM 호출**이 발생한다.

### 원인 5 — 부차적 커버리지 누락

표 캡션, 머리말/꼬리말(ctrl), 중첩표 바깥 셀 텍스트가 노드화되지 않아 약 5%의 텍스트가 인지 대상에서 빠진다. lineBreak/tab이 평탄화되어 다행(多行) 셀의 구조도 사라진다. 치명적이진 않으나 "양식 전체 인지"에는 구멍이다.

### 원인 6 — 신규 문서 생성 경로가 파이프라인에 미연결

"LLM 응답 내용으로 문서를 만들어 줘야 하는 것 아닌가"에 대한 답: **모듈은 있으나 배선이 없다.** `build_hwpx(spec)`은 `{title, paragraphs, tables}` 스펙으로 새 hwpx를 정상 생성하지만, 호출처가 테스트 픽스처와 데모 문서뿐이다. 오케스트레이터 의도 분류는 edit/fill/query 세 가지만 있어 "새 문서 만들어줘"가 들어와도 create 경로가 없고, API 라우트에도 생성 엔드포인트가 없다. 설계상 시나리오 C(신규 생성)로 계획됐으나 Phase 6에서 "여유 시" 항목으로 밀려 미연결 상태다.

## 3. 개선안

### 단기 (기존 계약 유지, 1~2주)

1. **빈 셀 쓰기 지원 — 최우선.** `apply_edits`에서 hp:t 없는 노드를 만나면 셀 내 기존 subList/p 구조에 hp:run+hp:t를 생성 삽입한다. `parse_section`이 이미 t_ns와 parent_map을 반환하므로 구조는 준비돼 있다. 같은 셀·이웃 셀 run의 charPrIDRef/paraPrIDRef를 복제하면 서식도 유지된다.
2. **스타일 기반 가이드 감지.** header.xml의 charPr를 파싱해 기울임+파란색 계열 id 집합을 만들고, 해당 charPrIDRef를 참조하는 run을 "guide"로 표시한다. TextNode에 `is_guide`, `guide_text`를 추가하고 채움 대상 정의를 "regex 토큰"에서 "guide 노드 + guide 인접 빈 셀 + regex 토큰"으로 확장한다. 가이드 문구 자체가 곧 작성 지시("…500자 내외 작성")이므로 프롬프트 재료로 그대로 쓴다.
3. **표 구조 노출.** get_nodes에 table_idx/row/col/span·section을 포함하고, 프롬프트는 평문 나열 대신 표 단위(라벨 행·열 포함 그리드)로 직렬화한다. 빈 셀에는 같은 행/열의 라벨 텍스트를 문맥으로 붙인다.
4. **프롬프트 규모 제어.** 채움/편집 프롬프트에서 대상 아닌 빈 노드는 제외하고, 청크를 "노드 30개"가 아니라 "표 1개 또는 절(제목~다음 제목) 1개" 단위로 나눈다.

### 중기 (파이프라인 구조 개선)

5. **2단계 채움 파이프라인 도입.**
   - 1단계 "양식 스키마 추출": 업로드 시 표·절 단위로 LLM에게 `{field_name, target_node_id, 작성지시(가이드 문구), 분량}` 필드맵을 만들게 해 문서별 1회 캐시. 이것이 "양식 인지"의 실체가 된다.
   - 2단계 "필드별 생성": 사용자 제공 자료(+RAG)로 필드맵을 순회하며 채움. 장문 필드는 분량 지시("공문서 문체 3~5문장")를 프롬프트에 명시.
   - 3단계 "검증": verify_output에 regex 잔존뿐 아니라 **가이드 스타일 run 잔존 검사**를 추가(양식 요구사항인 "가이드 삭제 후 제출"의 자동 확인).
6. **create 의도 배선 — 신규 문서 생성 연결.** 의도 분류에 `create`를 추가하고, LLM이 spec JSON(IR: title/headings/paragraphs/tables)을 출력하면 `build_hwpx`로 생성 → 이후 기존 편집 파이프라인에 인계한다. 서식 품질이 중요해지면 "스타일 시드 문서 + [[SEED:…]] 마커" 방식(프로젝트 개선 검토 사항 참조)으로 격상한다.
7. **커버리지 보강.** 캡션·머리말/꼬리말 노드화, lineBreak 보존, 개행→문단 분할 확장.
8. **실양식 회귀 테스트.** 이 서식1을 테스트 픽스처로 넣고 "노드 수·guide 수·빈 셀 채움 성공률"을 하드 게이트로 삼는다. 합성 템플릿만으로는 이번 두 병목(빈 셀 hp:t 부재, 스타일 가이드)이 재현되지 않음이 확인됐다.

## 4. UNI 서버 협의가 불가능할 때의 대응 (guided_json·max_tokens 없이 가기)

전제 정리: guided_json(서버 측 JSON 스키마 강제)은 "있으면 좋은" 보강이지 전제가 아니다. §3의 1~3번(빈 셀 쓰기, 가이드 감지, 표 구조 노출)은 전부 클라이언트 작업이라 서버와 무관하게 진행한다.

### 4.1 협의 없이 먼저 확인할 것 — passthrough 실험

`_chat_body`가 opts를 요청 바디에 병합하는 구조이므로, 서버가 추가 필드를 vLLM에 그대로 넘길 가능성이 있다. `probe_uni_rag.py`에 `max_tokens: 4096`(안 되면 `max_new_tokens`, `response_format`)을 실어 동일 질의 A/B 비교. 담당자 협의가 아니라 요청 몇 번으로 판별되며, 통하면 응답 잘림 문제가 파라미터 하나로 해결된다.

### 4.2 서버가 무시할 경우 — 클라이언트 측 대체 전략 4가지

1. **호출당 기대 출력을 서버 상한 아래로 설계.** max_tokens를 못 올리면 응답을 작게 쪼개 잘림 자체를 없앤다. 표 1개 단위 청킹, 장문 필드는 필드 1개당 호출 1회. 호출 수는 늘지만 잘림·파싱 실패가 구조적으로 사라진다. §3-4(표/절 단위 청킹)·§3-5(필드별 생성)와 같은 방향이라 별도 공사가 아니다.
2. **JSON 대신 줄 단위 프로토콜(JSONL 또는 `id⇥new_text`).** JSON은 끝 괄호 하나만 잘려도 전체가 깨지지만, 줄 단위는 응답이 중간에 잘려도 완성된 줄까지 전부 회수되고 잘린 마지막 줄만 버리면 된다. 미회수 id만 모아 후속 호출로 이어가면 스키마 강제 없이도 사실상 손실 없는 수집이 된다.
3. **검증-재요청 자가수정 루프 강화.** 현재 "파싱 실패 시 1회 재요청"을, Pydantic 모델(EditSpec) 검증 후 "무엇이 틀렸는지"를 오류 메시지로 되먹이는 루프 2~3회로 확장한다. 기존 4단계 복구 파서와 그대로 결합된다. EditSpec을 단일 원천(SSOT)으로 삼으면 추후 guided_json이 열렸을 때 스키마 재사용도 된다.
4. **프롬프트 예시를 실물 분량으로.** 예시 reply가 "한 줄 답변"이면 모델이 그 길이를 모방한다. new_text 예시를 실제 3~5문장 수준으로 교체하고, 필드 유형별 분량 지시(표 셀 1~2문장, 서술형 3~5문장)를 명시한다.

### 4.3 우선순위 (서버 협의 불가 시나리오)

passthrough 실험(4.1, 반나절) → 빈 셀 쓰기(§3-1) → 가이드 감지+표 구조(§3-2·3) → 줄 단위 프로토콜+검증 루프(4.2) → 2단계 파이프라인(§3-5). 이 순서면 UNI 서버는 손대지 않고 현재 스택 그대로 완주할 수 있다.

### 우선순위 근거

§3-1 없이는 어떤 개선도 무의미하다(쓸 수가 없으므로). §3-2·3이 "인지"를 해결하고, §3-4·§4가 안정성을 올린다. §3-5·6은 그 위의 품질 단계다.
